# ai-atlas — Collection Architecture

> Status: **Draft v1.0** — produced by the Builder (architect-designer agent unavailable in this environment; synthesis grounded in the OpenCode configuration spec, the Agent Skills ecosystem analysis, and validated product decisions).

## 0. Product decisions (locked)

| Decision | Choice | Rationale |
|---|---|---|
| Primary tool | **OpenCode** (ecosystem-compatible) | Target decided by owner; SKILL.md standard is portable |
| Language | **English** | AI models are predominantly trained on English; description-based triggering is more reliable |
| Granularity | **One skill = one competency** (~50 fine-grained skills) | Avoids the "kitchen-sink" skills observed in agent-skills; consistent grain |
| Organization | **By SDLC role** (foundation, architect, backend, frontend, ui-designer, tester, devops) | Mirrors team structure and SDLC stages |
| Namespacing | **Domain prefixes** (`fnd-`, `arch-`, `be-`, `fe-`, `ui-`, `tst-`, `ops-`) | Prevents collisions with existing collections (agent-skills, Superpowers, Pocock) when installed side-by-side |
| Distribution | **Standard `skills/<name>/SKILL.md` layout** → `npx skills add <owner>/<repo>` + native OpenCode folders + `install.sh` fallback | Zero custom tooling; covers 75+ agents via the Vercel Labs skills CLI |
| Positioning | **Engineering fundamentals, language-agnostic** (Clean Architecture, DDD, SOLID, patterns, microservices) — NOT another web/JS-centric clone | Fills the gaps identified in agent-skills (architecture phase under-represented, JS/TS-centric) |
| Agents | **Yes** — `.opencode/agent/*.md` subagents per role | Specialists compose with domain skills |

### Design rules for the structure

- **`skills/` is flat.** One folder per skill, named exactly after the skill. Rationale: the `npx skills add` CLI and every tool's skill scanner discover `skills/<name>/SKILL.md`; nested domain directories (e.g. `skills/backend/dev-x/SKILL.md`) are *not* uniformly supported across installers. Domain grouping is encoded in the name prefix, not the file tree.
- **Skills are self-contained.** A skill must work when installed alone. A `SKILL.md` MAY link only to files inside its own folder (`references/`). It MUST NOT link to root-level `references/` or to sibling skills. This structurally prevents the per-skill install breakage observed in agent-skills (#361).
- **`agents/` is a separate portable core.** The skills CLI does not install agents; they ship for OpenCode (`install.sh` → `.opencode/agent/`) and manual copy.
- **Everything else is tooling or docs.**

## 3. SKILL.md template & writing conventions

### Frontmatter (authoritative)

```markdown
---
name: be-saga-pattern
description: "Designs and implements distributed transactions with the Saga pattern: choreography vs orchestration, compensation, and idempotency guards. Use when a business operation spans multiple services, when you need distributed consistency without distributed transactions, or when you are debugging partial failures across services."
license: MIT
compatibility: opencode, claude-code, codex
metadata:
  domain: developer-backend
  sdlc-stage: implementation
  version: 1.0.0
---
```

Rules:
- `name`: required, lowercase-hyphen, ≤ 64 chars, **must equal the folder name**.
- `description`: effectively required for discovery. **English, third person, front-loaded triggers** — literally include the words/phrases a user would type ("Saga", "distributed transaction", "spans multiple services"). End with "Use when…". 2–3 sentences max. No trailing newline tricks.
- `license` / `compatibility` / `metadata`: optional but **expected** in this collection (auditability).
- Unknown fields route into `options` silently in OpenCode — never add experimental fields.

### Body anatomy (author handbook)

Target: **≤ 200 lines** per SKILL.md. If a section would exceed this, move detail into `references/` inside the skill folder.

| Section | Required | Guidance |
|---|---|---|
| `# <Title>` | yes | Start with the skill name (Title Case) |
| `## Overview` | yes | 2–5 lines: what, why, when the competency pays off |
| `## When to Use` | yes | Trigger bullets + explicit **When NOT to use** sub-block (anti-trigger discipline) |
| `## Process` | yes | Numbered steps, concrete thresholds, before/after examples. **Process, not prose.** |
| `## Common Rationalizations` | yes | Table: excuse agents give to skip a step × reality (3–6 rows) |
| `## Red Flags` | yes | Bulleted signs the skill is being applied wrong |
| `## Verification` | yes | Checkboxes the agent must tick; evidence-based exit criteria ("Seems right" never passes) |
| `## References` | optional | Relative links ONLY to `references/` inside this skill's folder |

### Progressive disclosure strategy

- Each skill keeps its depth in `references/` (loaded on demand by the model via reads — no auto-loading).
- **Self-containment is a hard rule**: never reference root `references/`, sibling skills, or absolute repo paths. This is how we avoid the agent-skills #361 portability bug by design rather than by patch.
- A skill must remain useful when installed **alone** (per-skill `npx skills add … --skill X`).

### Style rules

1. English, imperative voice, second person for the agent ("Verify…", "Do not…").
2. Concrete numbers over adjectives: "~100 lines per change" not "keep changes small".
3. Example before/after pairs in Process; examples > theory.
4. One competency per skill — if you need "and also", split it.
5. No executable promotion: skills may suggest commands the agent runs, but never instruct exfiltration, secret collection, or curl|bash of remote content.
6. Cross-references to other skills allowed as plain text mentions ("see `be-tdd`") — never load-bearing links.

## 4. Agents design

### Agent list (`.opencode/agent/<name>.md`)

| Agent file | Purpose | mode |
|---|---|---|
| `orchestrator.md` | Primary agent: routes work by SDLC stage, spawns specialists, enforces quality gates | primary |
| `arch-specialist.md` | Requirements→design, ADRs, architecture review | subagent |
| `backend-developer.md` | Backend implementation per `be-*`/`arch-*` skills | subagent |
| `frontend-developer.md` | Frontend implementation per `fe-*` skills | subagent |
| `ui-designer.md` | Research→flows→visual design per `ui-*` skills | subagent |
| `tester.md` | Test strategy/cases per `tst-*` skills | subagent |
| `devops-engineer.md` | CI/CD, infra, release per `ops-*` skills | subagent |
| `code-reviewer.md` | Multi-axis review per `fnd-code-review` | subagent |

### Frontmatter (authoritative, per agent)

```markdown
---
description: "Senior backend developer: implements features per the be-* and arch-* skills, writes tests first, and verifies before handing off."
mode: subagent
permission:
  edit: allow
  bash: ask
---
```

- `model`: **leave unset** in shipped files — users let their default apply; we document recommended models in docs, never hard-pin.
- `mode: primary` only for orchestrator; everything else `subagent`.
- Default `permission` for specialists: read/write edits allowed but **bash: ask** (safety-first). Code-reviewer and arch-specialist default `edit: deny` (read-only reviewers); document how to relax.
- Body = the persona prompt. **Composition rule:** the prompt points to the agent's domain skills ("Load and follow the relevant `be-*` skill") — it never restates skill content. Skills are the knowledge layer; agents are the persona + permission + focus layer. This prevents content duplication.

## 5. Install & distribution strategy

### Primary: `npx skills add` (ecosystem standard)

```
npx skills add kouassives/ai-atlas                # all 54 skills
npx skills add kouassives/ai-atlas --skill be-tdd  # single skill
npx skills add kouassives/ai-atlas --list         # browse
```

- The flat `skills/<name>/SKILL.md` layout is exactly what the skills CLI scans (mirrors agent-skills). ✓
- The CLI writes to each tool's native directory (OpenCode, Claude Code, Codex, Cursor, …75+). ✓

### Native OpenCode paths

- Skills: copy `skills/*` → `.opencode/skills/` (project) or `~/.config/opencode/skills/` (global).
- Agents: copy `agents/*.md` → `.opencode/agent/`.
- Compatibility: OpenCode auto-loads `.claude/skills/**/SKILL.md` and `.agents/skills/**/SKILL.md` — the same skill folders work unmodified on Claude Code / Codex users. ✓

### Fallback: `install.sh` (POSIX sh, no deps)

```
./install.sh                      # global → ~/.config/opencode/
./install.sh --project            # → ./.opencode/
./install.sh --list               # preview what would be copied
./install.sh --dry-run            # simulate
./install.sh --agent claude-code  # target another tool's folder
./install.sh --force              # overwrite
```

Copies `skills/*` and `agents/*` to the target scope; idempotent; never deletes unknown files; prints a manifest of installed components.

### Phase 2 (post-MVP): marketplace manifests

- Single source of truth: `registry.yaml` generated from `skills/` + `agents/`.
- Scripts emit `.claude-plugin/marketplace.json` and `.agents/plugins/marketplace.json` → native `/plugin marketplace add` installs on Claude Code and Codex.
- Out of scope for the first release.

### Guarantees

- Any skill installed by any mechanism works standalone (self-containment rule).
- No tool-specific syntax inside skill bodies (Markdown-only).
- Nonstandard frontmatter fields are forbidden (breaks strict validators).

## 6. Quality framework

### Tier 1 — Structural lint (`scripts/lint-skills.mjs`, runs on every PR)

Per skill folder, fail on:
- `name` ≠ folder name; name not lowercase-hyphen; name > 64 chars
- Missing/blank/≤20-char `description`
- Missing required sections (Overview, When to Use, Process, Common Rationalizations, Red Flags, Verification)
- Files other than `SKILL.md`, `references/*.md`, `assets/` inside the folder (no stray scripts)
- Markdown links escaping the skill folder (self-containment violation)
- `curl … \| sh`, `pipe to bash`, "exfiltrate", "send to attacker", "steal" patterns (security lint)
- SKILL.md > 200 lines (warning → error above 250)

### Tier 2 — Routing evals (`scripts/eval-routing.mjs`, runs in CI)

- `evals/routing/prompts.json`: realistic user prompts (e.g. *"our order flow touches 3 services and sometimes fails halfway — fix it"*) mapped to expected skill(s).
- Checks per prompt: (a) ≥1 skill description matches (no orphans); (b) exactly the intended skill(s) match — **collision detection** (two skills claiming the same domain forces a description disambiguation change).
- Deterministic: keyword + semantic overlap scoring over descriptions only. Zero LLM cost in CI.

### Tier 3 — Execution evals (`evals/cases/<skill-name>.md`, manual + smoke in CI)

- Each case: scenario, expected trace markers ("agent wrote a verification checklist", "agent asked for the missing constraint").
- CI smoke: skill loads in a headless OpenCode config, frontmatter parses, trigger keywords present.
- Full behavioral runs: documented manual procedure (`docs/usage.md#eval`) against real OpenCode sessions.

### CI pipeline (`.github/workflows/ci.yml`)

```
PR → Tier 1 lint → Tier 2 routing evals → install smoke test (temp .opencode layout) → SKILLS.md freshness check
release (tag v*) → gen-index → SHA256SUMS → GitHub release asset
```

## 7. Security posture

1. **No executable scripts inside skills.** Skills contain instructions and suggested commands only; no repo-side code runs on install.
2. **Content security lint** (Tier 1): block instructions that exfiltrate secrets/env vars or pipe remote content to a shell.
3. **Review gate:** every skill PR requires a reviewer pass checking the security lint + provenance of any third-party examples.
4. **Trust statement in README:** skills are instructions — review before installing; pin installed versions; treat downloaded skills like executable code (ecosystem consensus, see Bruniaux guide).
5. **Supply chain:** releases are tagged with SHA256SUMS generated in CI; no secrets in repo; CI uses least-privilege tokens.
